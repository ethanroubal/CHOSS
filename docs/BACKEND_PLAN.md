# Backend plan

How CHOSS moves from sample data on the phone to real servers: what's stored where, how it
stays fast, what's already built, and what's left (for you and in code).

## Services

| Need | Service | Why |
| --- | --- | --- |
| Database, sign-in, security rules, server functions | **Supabase** (Postgres) | One service for data, auth and permissions. Postgres handles our relationships (follows, likes, leaderboards) well, and search and map queries run in the database. |
| Videos | **Mux** | Upload straight from the phone, automatic transcoding to adaptive streaming (HLS), thumbnails, and a global CDN. Hosting video ourselves would mean building all of that. |
| Pictures (avatars, community photos) | **Supabase Storage** | CDN-backed, resizes on request (a 400 px thumbnail for grids, full size when opened), and the same security rules as the database. |
| Sign-in | **Sign in with Apple** (+ email) via Supabase Auth | Apple requires Sign in with Apple if you offer other social logins; it's also the smoothest option on iPhone. |
| Later | Push notifications (APNs), crash reporting (e.g. Sentry) | Not needed to launch a beta. |

Cloudflare Stream is a fine alternative to Mux, and Firebase to Supabase. The schema and design
below assume Supabase + Mux.

## What's stored

Everything the app shows, and where it lives. "Counter" means it's kept up to date on the
row automatically, so screens never count rows at read time.

| Data | Where | Contents |
| --- | --- | --- |
| **Profiles** | `profiles` | username (unique, case-insensitive), display name, bio, avatar path, bouldering / rope grade range, show-grade / show-hardest-send / show-projects settings. Counters: followers, following, places followed, posts. |
| Home gyms / crags | `profile_home_places` | up to 3, in order |
| **Places** (gyms, crags) | `places` | name, gym / crag, town / state / country, latitude / longitude, disciplines, about, source, verified, who added it. Counters: followers, posts. Cover photo (most-liked community photo). |
| **Climbs** | `climbs` | crag, name, area / wall, discipline, guidebook grade, about, verified, who added it. Counter: posts. Cover photo. |
| **Posts** (sends) | `posts` | author, place, climb, route name (board problems), discipline, send style, proposed grade, caption, video status and Mux ids, duration, aspect ratio. Counters: likes, comments, reposts, views. Soft-deleted. |
| **Videos** | Mux | the video files; the app streams `stream.mux.com/<playback id>.m3u8` and shows `image.mux.com/<playback id>/thumbnail.jpg` |
| Community grade | `climb_grade_votes`, `climb_grades` | running totals of proposed grades per climb, so the average is instant |
| Likes, reposts, follows (people and places), projects | one table each | one row per relationship, e.g. (post, user) |
| Comments | `comments` | post, author, text |
| Views | `posts.view_count` + `post_view_dedupe` | one view per viewer per post per day |
| **Community photos** | `community_photos`, `photo_likes` + Storage `community-photos/<user>/…` | place or climb, uploader, file path, size. Counter: likes. |
| Avatars | Storage `avatars/<user>/…` | |
| Grades reference | `grades` | every grade on every scale, with its rank and its comparable rank (Font → V, French / British → YDS), generated from the app so both agree |
| Safety | `reports`, `user_blocks` | reporting content and blocking people (App Store requirement for user-generated content) |

The schema is in `supabase/migrations/`. The 3,663 bundled gyms and crags are in
`supabase/seed.sql`, generated by `scripts/export_backend_seed.py`.

## Keeping it fast

**Writes are one row.** A like, follow, repost, project or view is a single insert or delete
on a primary key. Counters on the parent row (likes on a post, followers on a place…) are
updated in the same transaction by triggers. Posting a send is one insert; the video uploads
separately (below).

**Reads use an index in the order they're shown.** Home feed, a place's sends, a climb's
videos, a profile's grid, liked videos, trending, popular places, followers: each has an
index sorted the way the screen lists it. Lists load a page at a time with keyset pagination
("the next 20 after this one"), which stays fast however deep you scroll.

**Search, map and Legends run in the database.**
- Search uses trigram indexes, typo-tolerant like the app's current search, and returns the
  top matches in milliseconds.
- The map asks only for places inside the visible rectangle, using a spatial index.
- Legends and community grades come from running totals, not from scanning every send.

**Video never touches our servers.**
1. The app asks `create-video-upload` for an upload URL.
2. It uploads the file straight to Mux in the background, so it survives the app closing.
3. Mux transcodes it, and `mux-webhook` marks the post ready.

Playback is adaptive (lower quality on weak signal) and served from Mux's CDN. Thumbnails load
instantly as images.

**Pictures come from a CDN at the size needed.** For example, 300 px for a grid tile, 1600 px
full screen.

**The app stays instant.**
- Keep the current optimistic updates: the bicep fills immediately and the server catches up.
- Cache what was last seen on the phone, so screens open with content and refresh in the
  background.
- Pre-load the next page before you reach the end of a list.

## Security

- **Row Level Security on every table.** Anyone can read public content, and people can only
  create, change or delete their own rows. Some examples:
  - Only the uploader can delete a photo.
  - Only the author can delete a post.
  - Projects are hidden when the owner turns them off.
- **Clients can't write counters, verification flags or video fields at all** (column
  permissions). Only triggers and server functions can.
- **Secrets stay on the server.** The Mux keys and the Supabase service key only exist in
  server functions. The app ships with just the public "anon" key.

## What's built

| File | What it is |
| --- | --- |
| `supabase/migrations/20261001000000_initial_schema.sql` | Tables, indexes, counter triggers, security rules, and server functions: `home_feed`, `search_places` / `search_climbs` / `search_profiles`, `places_in_box`, `legends_most_sends`, `legends_hardest`, `record_view`, `delete_post` |
| `supabase/migrations/20261001000100_grades.sql` | Every grade and its comparable rank (generated) |
| `supabase/migrations/20261001000200_storage.sql` | Picture buckets and their upload / delete rules |
| `supabase/seed.sql` | The 3,663 gyms and crags (generated) |
| `supabase/functions/create-video-upload` | Creates the post and a Mux upload URL |
| `supabase/functions/mux-webhook` | Marks posts ready when Mux finishes (signature-checked) |
| `supabase/functions/delete-account` | Deletes a user and their data (App Store requirement) |
| `scripts/test_backend_locally.sh` + `supabase/tests/` | Applies everything to a local Postgres and checks behaviour as signed-in users |

The local test checks that everything applies cleanly, and that:
- counters go up and back down;
- search handles typos ("yosmite" → Yosemite) and towns;
- the feed and Legends follow the app's rules;
- clients can't write counters, like as someone else, or delete other people's posts and photos.

## What you need to do

1. **Supabase:** create an account and a project.
   - Pick the region closest to most users (e.g. US East).
   - Create two projects, `choss-dev` for testing and `choss-prod` for the App Store, so tests
     never touch real users.
   - Share the **Project URL** and **anon (public) key**. These go in the app and are safe to
     share.
   - Never share the service-role key or database password, or commit them to the repo.
2. **Mux:** create an account and a production environment.
   - Create an **API access token** with Mux Video read/write, and keep the token ID and
     secret private.
   - Add a **webhook** pointing at `https://<your project>.supabase.co/functions/v1/mux-webhook`
     and copy its signing secret.
3. **Apple Developer Program:** join it (needed for TestFlight and the App Store anyway).
   - Enable **Sign in with Apple** for the app's bundle id.
   - Create a Services ID and key for Supabase's Apple provider; Supabase's Auth → Providers →
     Apple page walks through it.
4. **Put the secrets in Supabase:**
   - In Project Settings → Edge Functions → Secrets, set `MUX_TOKEN_ID`, `MUX_TOKEN_SECRET`
     and `MUX_WEBHOOK_SECRET`.
   - Or do it from the terminal: `supabase secrets set MUX_TOKEN_ID=… MUX_TOKEN_SECRET=… MUX_WEBHOOK_SECRET=…`.
5. **Load the schema** with the Supabase CLI (`brew install supabase/tap/supabase`):
   ```sh
   supabase login
   supabase link --project-ref <project ref>
   supabase db push                      # applies supabase/migrations
   psql "<connection string>" -f supabase/seed.sql   # the gyms and crags
   supabase functions deploy create-video-upload
   supabase functions deploy delete-account
   supabase functions deploy mux-webhook --no-verify-jwt
   ```
6. **Write a privacy policy and terms, and host them at a URL.** The App Store requires both
   for sign-up and user content.
7. **Decide who moderates.** Someone needs to review reported content and verify user-added
   places and climbs. A simple admin view can come later.

**Costs:**
- Supabase and Mux both have free tiers that cover development and a small beta.
- In production, expect Supabase's Pro plan (a flat monthly fee) plus Mux usage, which is
  charged per minute of video stored and streamed.
- Check both pricing pages for current numbers. Video streaming will be the main cost as
  usage grows.

### Set up the test project (do production the same way when ready)

1. **Install the Supabase CLI and link the project.** Everything runs from the repo folder on
   your Mac:
   ```sh
   brew install supabase/tap/supabase
   supabase login
   supabase init                                   # once; answer "N" to the VS Code questions
   supabase link --project-ref qwnoanczqsqcygpjauoa
   ```
2. **Create the database:**
   ```sh
   supabase db push
   ```
   This applies everything in `supabase/migrations`: tables, security rules, grades and
   picture storage.
3. **Load the 3,663 gyms and crags:**
   ```sh
   psql "$(supabase db url --linked)" -f supabase/seed.sql
   ```
   If `db url` isn't available in your CLI version, copy the connection string from the
   dashboard (Connect → Session pooler) and use that in place of `$(...)`.
4. **Configure sign-in** in Supabase → Authentication:
   - **Email:** on by default. For quick testing you can turn off "Confirm email" (Sign In /
     Providers → Email); turn it back on for production.
   - **Apple:** turn on the Apple provider and follow its instructions (Services ID, key from
     your Apple Developer account). In Xcode, add the **Sign in with Apple** capability to the
     CHOSS target (Signing & Capabilities → + Capability).
5. **Deploy the server functions:**
   ```sh
   supabase functions deploy delete-account
   supabase functions deploy create-video-upload
   supabase functions deploy mux-webhook --no-verify-jwt
   ```
   Posting videos needs a Mux account. Set its secrets with
   `supabase secrets set MUX_TOKEN_ID=… MUX_TOKEN_SECRET=… MUX_WEBHOOK_SECRET=…` and add the
   webhook in Mux. Until then, everything else works, but posting a send fails with an error.
6. **Open the project in Xcode.** It fetches the Supabase library the first time
   (File ▸ Packages ▸ Resolve Package Versions if it doesn't), then run. You should see the
   sign-in screen.

## Next steps in code

In order; each step can ship on its own.

1. **Done: sign-in and profiles.**
   - Sign in with Apple and email.
   - First-time profile setup, saved to `profiles`.
   - Sign out and Delete account in Settings.
2. **Done: a Supabase repository.** `SupabaseClimbingRepository` implements the existing
   `ClimbingRepository`, so the views didn't change.
   - It writes straight to the tables.
   - For now it loads one snapshot at launch: all places and climbs, the latest 400 sends plus
     your own, and the people, likes, comments, follows, photos and projects involved.
3. **Load by page, not everything at once.** Today the app loads one snapshot of everything.
   With real data it should load what each screen needs:
   - the home feed via `home_feed`, 20 at a time;
   - a place's sends, a climb's videos and a profile's grid by page;
   - search via the search functions;
   - the map via `places_in_box`.

   `AppStore` keeps its optimistic updates and adds a small on-device cache so screens open
   instantly.
4. **Video upload and playback.**
   - Upload through `create-video-upload` with a background upload to Mux, showing
     "Processing…" on your post until it's ready.
   - Play Mux HLS URLs, with thumbnails from Mux.
5. **Pictures:** upload avatars and community photos to Storage, and load resized versions.
6. **Likes, views, follows, projects and comments** write to their tables and call
   `record_view`. Counters come back with each page.
7. **Safety:** report and block buttons (posts, comments, photos, profiles), hiding blocked
   people, and a way to review reports.
8. **Before launch:**
   - rate limits on uploads;
   - a nightly job to purge deleted posts' videos from Mux;
   - backups (Supabase Pro has daily backups);
   - crash reporting;
   - TestFlight beta.
9. **Later:**
   - push notifications ("3 new sends at your gym");
   - a precomputed feed if it gets large;
   - moving popularity rankings to scheduled jobs;
   - PostGIS for map clustering.
